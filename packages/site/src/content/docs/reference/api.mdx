## ireko

The core: the model, the engine, the strategies, the routers and the builder. It imports nothing.

### Layout

```ts
function layout(input: LayoutInput, options?: LayoutOptions): Layout;
function createEngine(config?: EngineConfig): Engine;

interface Engine {
  layout(input: LayoutInput, options?: LayoutOptions): Layout;
  extend(config: EngineConfig): Engine;
  readonly strategies: ReadonlyMap<string, AnyStrategy>;
  readonly routers: ReadonlyMap<string, Router>;
  readonly limits: Limits;
}

class IrekoError extends Error {
  readonly issues: readonly Issue[]; // the findings with the severity "error"
}
```

`layout` uses a shared engine with the built-in strategies and routers. It throws only in the strict mode, or for an input that is not an object with a root.

The option `linkedShape` of `EngineConfig` sets the code that gives the shape of a linked node. The default is the code of `ireko`. This option and its types `LinkedShape` and `ShapePart` have the tag `@beta`, so a release can change them.

### The builder

```ts
const grid: Builder<GridOptions>;
const radial: Builder<RadialOptions>;
const tree: Builder<TreeOptions>;
const layers: Builder<LayersOptions>;
function builder<O>(type: string): Builder<O>; // a builder for a strategy that you register
function node(id: string, options?: Omit<ContainerOptions, "gap" | "padding" | "header">): NodeSpec;

type Child = NodeSpec | string; // a node, or the identifier of a leaf
type BuildOptions<O> = Partial<O> & ContainerOptions;
interface ContainerOptions { label?; size?; fit?; data?; gap?; padding?; header? } // each container has these options, for each strategy

interface Builder<O> {
  (id: string, ...children: readonly Child[]): NodeSpec;                         // a linked node
  (id: string, options: BuildOptions<O>, ...children: readonly Child[]): NodeSpec;
  nested: {                                                                      // a container
    (id: string, ...children: readonly Child[]): NodeSpec;
    (id: string, options: BuildOptions<O>, ...children: readonly Child[]): NodeSpec;
  };
}
```

A string child is a leaf with that identifier. The options object of a builder has the options of the strategy, and `label`, `size`, `fit`, `data`, `gap`, `padding` and `header`.

### Strategies and routers

```ts
function defineStrategy<O>(strategy: Strategy<O>): Strategy<O>;
function defineRouter(router: Router): Router;
const gridStrategy: Strategy<GridOptions>;
const radialStrategy: Strategy<RadialOptions>;
const treeStrategy: Strategy<TreeOptions>;
const layersStrategy: Strategy<LayersOptions>;
const BUILTIN_STRATEGY_NAMES: readonly string[]; // grid, radial, tree, layers
const straight: Router;
const orthogonal: Router;
const avoid: Router;      // around the other boxes
const builtinStrategies: readonly AnyStrategy[];
const builtinRouters: readonly Router[];
const defaultLimits: Limits; // { maxNodes: 100000, maxDepth: 10000, maxChildren: 10000 }

function borderPoint(box: Rect, toward: Point): Point; // where the line to a point leaves a box
function defaultsOf<O>(schema: OptionSchema<O>): O;
```

[Write a strategy](/learn/custom-strategy/) has the contract of `Strategy`, and [edges](/learn/edges/#write-a-router) has the contract of `Router`. These types are the inputs and the outputs of those contracts.

```ts
interface ArrangeInput<O> { id; mode: Mode; self: Size; children: readonly MeasuredChild[]; options: O; gap; depth; edges?: readonly ChildEdge[] } // the input of Strategy.arrange
interface Arrangement { direction?: Direction; flow?: Direction; offsets: readonly Point[]; content?: Rect } // the output of Strategy.arrange
interface AuditInput<O> { node: PlacedNode; children: readonly PlacedNode[]; options: O; gap } // the input of Strategy.audit, with absolute rectangles
interface RouteInput { id; kind: "tree" | "extra"; source: Rect; target: Rect; direction?: Direction; obstacles?: readonly Rect[] } // the input of Router.route, with absolute rectangles
interface MeasuredChild { id; box: Size; extent: Rect; mode: Mode; shape?: Shape } // a child after the measure pass
interface ChildEdge { from; to } // an edge between the subtrees of two children, as their indexes
interface Shape { rows: readonly Band[]; columns: readonly Band[] } // the shape of a subtree, relative to the top-left corner of its root box
interface Band { from; to; min; max } // one band of a shape
type Direction = "down" | "up" | "left" | "right"; // the direction from a node to its children

type OptionSpec = NumberOption | BooleanOption | EnumOption; // the schema of one option
interface NumberOption { type: "number"; default: number; min?; max?; integer?; description }
interface BooleanOption { type: "boolean"; default: boolean; description }
interface EnumOption<V extends string = string> { type: "enum"; values: readonly V[]; default: V; description }
type OptionSpecFor<T> = [T] extends [number] ? NumberOption : [T] extends [boolean] ? BooleanOption : [T] extends [string] ? EnumOption<T> : never;
```

Between `from` and `to` on one axis, a subtree is between `min` and `max` on the other axis. In the rows of a shape, `from` and `to` are y values. In the columns, they are x values. A tidy strategy uses the shape to put a subtree closer to its neighbors than the extent permits.

### The model

```ts
interface LayoutInput { root: NodeSpec; edges?: EdgeSpec[] }
interface NodeSpec { id; label?; layout?; mode?; fit?; size?; children?; data? }
interface EdgeSpec { source; target; id?; label?; data? }

interface Layout {
  nodes: PlacedNode[];  // in paint order: each container before the boxes inside it
  edges: PlacedEdge[];
  bounds: Rect;
  issues: Issue[];
}
interface PlacedNode extends Rect {
  id; label; parent?; container?; depth; mode; layout; scale; clip; childCount; data?;
}
interface PlacedEdge { id; source; target; kind: "tree" | "extra"; points: Point[]; label?; data? }

type LayoutRef = string | LayoutWithOptions; // the name of a strategy, or the name with options
interface LayoutWithOptions { type: string; [option: string]: unknown }
type Mode = "nested" | "linked"; // the children are inside the box of the node, or around it
type Fit = "grow" | "scale" | "clip";
type TreeEdges = "linked" | "all" | "none"; // the tree edges that the engine adds
type Severity = "error" | "warning"; // an error changes the output, and a warning does not
type IssueCode = "DUPLICATE_ID" | "EMPTY_ID" | "UNKNOWN_LAYOUT" | "UNKNOWN_ROUTER" | "INVALID_OPTION" | "INVALID_SIZE" | "UNKNOWN_EDGE_END" | "SELF_LOOP" | "LIMIT_NODES" | "LIMIT_DEPTH" | "LIMIT_CHILDREN" | "STRATEGY_FAILED" | "ROUTER_FAILED" | "OVERLAP" | "ESCAPE" | (string & {});
interface TraceEvent { phase: "normalize" | "measure" | "place" | "route" | "audit"; data: unknown } // the output of one phase of the pipeline
```

All types are plain data. JSON holds each value with no loss.

With the fit `grow`, the container grows to fit its content. With `scale`, the content becomes smaller to fit the container. With `clip`, the content keeps its size and the renderer cuts it at the edge of the container.

### Label sizes

```ts

interface FitTextOptions { fontSize?; padding?: { x; y }; minWidth?; minHeight?; widthOf? }
```

### Geometry

`Point`, `Size` and `Rect`, and small functions on them: `centerOf`, `union`, `unionAll`, `translate`, `inflate`, `overlaps`, `contains`, `rectAt`.

## ireko/shapes

The layout of `ireko`, with the shapes of linked nodes from a module of the Vex compiler. It gives the same layout, to the bit. This entry shows the module of Vex. `ireko` is the choice for production use.

```ts
function layout(input: LayoutInput, options?: LayoutOptions): Layout;
```

The bundle of this entry is <Size of="ireko/shapes: layout" /> with gzip. The bundle of `ireko` is <Size of="ireko: layout" />. These sizes come from the build of this page.

This table gives the time of a layout with this entry, divided by the time with `ireko`. A value above 1 is slower. The A/A column is a second copy of `ireko`, and it shows the noise of the measure.

| Input | A/A | `ireko/shapes` |
| --- | --- | --- |
| Full tree, 111 nodes | 1.013 | 1.098 |
| Full tree, 1111 nodes | 1.001 | 1.026 |
| Full tree, 11111 nodes | 1.006 | 1.073 |
| Examples | 0.995 | 1.026 |
| Random trees | 0.999 | 0.990 |

This table is a fixed study of ireko 0.1.4, from the commit `1d575a6` of 2026-11-04. It tells nothing about a newer release. The entry is slower on full trees and on the examples, and 1 % faster on random trees. The values are medians of 9 processes with 31 rounds each, on Node 24 in CI. Both layouts run in one process, so one call in the measure pass receives two functions. A program that imports one entry does not have this condition, and this measure does not give its time.

## ireko/react

```tsx
function useLayout(input: LayoutInput, options?: LayoutOptions, engine?: Engine): Layout;
function LayoutSvg(props: LayoutSvgProps): ReactElement;
function LayoutView(props: LayoutViewProps): ReactElement;
interface LayoutSvgProps { layout; theme?; padding?; title?; className?; style? }
interface LayoutViewProps { layout; renderer?: RendererKind; theme?; viewport?; duration?; interactive?; selected?; onPick?; className?; style? }
type RendererKind = "svg" | "dom" | "canvas"; // the live renderers of LayoutView
```

`useLayout` makes the layout again only when `input`, `options` or `engine` change, so keep them in a memo or a state. `LayoutSvg` has no state and no effects. `LayoutView` mounts a live renderer in an effect.
